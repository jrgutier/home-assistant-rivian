# Parallax schemas: the `.proto` files, and how a topic gets decoded

Since s49 the Parallax decoders parse with classes generated from `.proto`
schemas. Before that every decoder walked varints by hand, carrying its own copy
of a message's field numbers, and the `.proto` files beside them were
documentation. `PARALLAX_DECODERS.md` is still the record of *how each layout was
recovered from the app*; this file is how the result is now stored and used.

The structure follows bretterer/rivian-python-client PR 205 (commit `91b41cf`,
unmerged when s49 was written). PR 205 is a **template, not a source**: where its
schema and this integration's decoder disagreed, the decoder won, and where the
decoder and the decompiled app disagreed, the app had already won in an earlier
story.

## Layout

```
custom_components/rivian/rivian_client/parallax/
├── __init__.py     RVM_DECODERS (the live table), decode_parallax_message, re-exports
├── core.py         RVMDecoder registry; _fields / _name helpers
├── <prefix>.py     one module per topic prefix: body, charging, comfort, ...
├── commands.py     RVMType, ParallaxCommand, build_*, encode_climate_hold_setting
├── _wire.py        the old hand-rolled walker -- a tool, used by no decoder
└── proto/
    ├── <prefix>.proto      20 schemas
    ├── <prefix>_pb2.py     generated, committed, shipped
    └── <prefix>_pb2.pyi    generated, committed, not shipped
```

A decoder is written against a parsed message and registered with its class:

```python
@RVMDecoder.register(body_pb2.TrailerState, "body.trailer.state")
def decode_trailer_state(m: body_pb2.TrailerState) -> dict[str, Any]:
    return _fields(m, {"presence": ("trailerStatus", _TRAILER_PRESENCE_MAP)})
```

`register` returns what callers have always called: a function that takes the
base64 payload and returns a dict, `{}` when there is nothing to say. The empty
check, base64, parsing and the catch-all that stops one bad frame taking the
subscription down are in that wrapper, once.

## Regenerating

```sh
scripts/regen_proto.sh            # regenerate in place
scripts/regen_proto.sh --check    # regenerate, fail if anything changed
```

`--check` runs in pre-commit and in CI. The generator is `grpcio-tools==1.80.0`,
pinned in `requirements_test.txt`.

**The generator version is a decision about which Home Assistant releases can
load the integration.** Every `*_pb2.py` validates the protobuf runtime when it is
imported and raises if the runtime is *older* than the protoc that wrote it. That
is what took the integration down during vendoring. So four things are one
decision and must move together:

| where | value | says |
|---|---|---|
| `scripts/regen_proto.sh` `STAMP` | `6.31.1` | generated code may be no newer than this |
| `manifest.json` | `protobuf>=6.31.1,<8` | the runtimes that code loads on |
| `hacs.json` | `2025.6.0` | the first Home Assistant whose constraint is 6.31.1 |
| `tests/client/test_proto_generated.py` | all three | fails when they disagree |

Measured from `homeassistant/package_constraints.txt` at each tag: 5.29.2 through
2025.5.3, **6.31.1 from 2025.6.0**, 6.32.0 from 2025.9.0. Home Assistant core does
not depend on protobuf, it only constrains it, which is why the manifest has to
declare it.

The `<8` is not caution. protobuf guarantees a runtime loads code generated by the
previous major version and no further back, so 6.x code works under 7.x and stops
at 8. Declared, that is an install-time conflict; undeclared, it is an import-time
failure. Checked, not assumed: on 2026-10-06 the built zip imported cleanly under
protobuf 7.36.2, the newest release (`LOAD_TEST_PROTOBUF=7.36.2
scripts/load_test.sh`). **Regenerate before Home Assistant reaches protobuf 8.**

`scripts/load_test.sh` imports every module out of the built zip under the
protobuf Home Assistant pins, and again with `LOAD_TEST_PROTOBUF=floor` under the
oldest the manifest admits. CI runs both.

Each schema is registered in protobuf's process-wide descriptor pool under its
full `custom_components/rivian/...` path and a `rivian_ha.parallax.*` package. The
pool rejects two different files with one name; upstream's files are
`rivian/parallax/proto/*.proto` in package `rivian.parallax.*`, and a bare
`body.proto` could collide with anything.

## The three rules a schema here follows

These are why the schemas differ from PR 205's, and each exists to keep a decoder
reporting exactly what it reported before.

**`optional` where the decoder reports a field only when it was sent.** proto3
does not put a zero on the wire, and a plain field reads back as zero either way,
so without `optional` "sent as 0" and "not sent" are the same thing. They are not
the same thing to these decoders: `dynamics.vehicle.gear` with gear 0 is
`not_defined`, and with no gear field it is nothing at all. `_fields` in `core.py`
requires it.

**`uint64` where the decoder passes an integer straight through.** The old walker
handed decoders the raw varint, 64 bits unsigned, whatever the app's type. A
narrower declared type changes the number for values outside it -- a negative
`int32` such as a Wi-Fi signal in dBm arrives as a ten-byte varint, and reads as
`-60` through `int32` where the old decoder reported `18446744073709551556`. Wrong
before, but *changing* it is a behaviour change, and s49 made none. The app's type
is in the comment beside each one.

**No declaration for a length-delimited field nothing reads.** An undeclared field
is kept as an unknown field and costs nothing. A declared one whose type is
guessed wrong -- a `string` that is not UTF-8, a submessage that is not that
message -- fails the parse of the *whole message*, and takes down fields that
decoded fine before. PR 205 declares many such fields; here each is a comment
naming what upstream thinks it is.

The encode side has the opposite need. `ClimateHoldSetting` and the operation
envelope are **not** `optional`, so a zero still serialises to nothing.

## Adding a topic

1. **Get a frame.** `scripts/capture_rvm_frames.py` (read-only; see
   `RVM_FIXTURES.md`). A decoder without a frame renders wrong values as
   confidently as right ones.
2. **Write the message** in `proto/<prefix>.proto`, from the app
   (`PARALLAX_DECODERS.md` for the method), following the three rules. If the
   topic is one of the eighteen below, the message is already there -- check it
   against the frame before trusting it.
3. `scripts/regen_proto.sh`, and commit the `.proto`, `_pb2.py` and `_pb2.pyi`
   together.
4. **Write the decoder** in `<prefix>.py` with `@RVMDecoder.register`. Use
   `empty_payload=True` only if an empty payload means something for this topic.
5. **Test it against the captured frame**, and add the frame to
   `tests/client/fixtures/parallax/` so `test_parallax_schema_parse.py` checks the
   schema against it.
6. **Stop here until it is verified on hardware.** Steps 1-5 change nothing the
   vehicle can see.
7. **Go live:** add the topic to `RVM_DECODERS` in `parallax/__init__.py`.
   `coordinator.SUBSCRIBED_RVMS` is derived from that table, so this line makes
   the vehicle open a subscription. That is why the table is written out and not
   read off the registry: registering and going live are separate, reviewable
   steps. `tests/client/test_parallax_registry.py` fails while the two disagree,
   so a registered decoder cannot be forgotten in either direction -- land steps
   4 and 7 together, after 6.
8. Add the topic to the four lists in
   `tests/client/fixtures/parallax_golden/surface.json` by hand, in the same
   commit. That file is the record of what the vehicle is asked for, and a change
   to it should be a line in a diff. Do **not** touch `golden.jsonl`: it is the
   frozen behaviour of the pre-s49 decoders, and a decoder written after s49 has
   no entry in it.

## What changed in behaviour: nothing a vehicle can send

The rebuilt decoders are held to the old ones by a recorded corpus
(`RVM_FIXTURES.md`, "The golden corpus"): 5,740 payload → output cases, of which
5,551 are reproduced exactly. The remaining 189, and every disagreement found by
feeding both decoders 773,184 hostile payloads (`scripts/parallax_differential.py`),
fall into three classes. No encoder produces any of them.

| class | what it is | old | new | seen |
|---|---|---|---|---|
| rejected | not a valid encoding of the topic's message: cut short, a submessage field holding bytes that are not a message, a `string` that is not UTF-8 | reported whatever it had read before the damage | `{}` | 283,080 |
| repeated | a single-valued field sent more than once | first, last, or a mixture, decoder by decoder | last, by specification | 768 |
| wide | a varint too large for the field's declared 32-bit type | passed 64 bits on | truncated | 169 |

Unexplained: **0**.

`rejected` is by far the largest because the differential cuts every payload short
at every byte. It is also the one worth understanding: the walker was lenient by
accident, and a truncated frame used to yield a partial -- and possibly wrong --
decode. It now yields nothing, and the coordinator keeps the previous value.

`repeated` is almost entirely `vehicle.network.state`, the one decoder that
accepts a field in either wire type (see the comment on `_network_part` in
`vehicle.py`): when a field arrives both ways in one message, which one wins is no
longer the wire order.

**Against the vehicle.** `scripts/parallax_differential.py --live 150` asks the
same question of real frames: it subscribes read-only to all 57 decoded topics,
holds what arrives in memory, and prints only whether the two decoders agree and
whether each frame fits its schema. On 2026-10-06, against the owner's R1T, 52 of 57
topics published; the decoders agreed on every frame and every frame fit its
schema. The five silent topics (`body.windows.states`, the pet snapshot, the
immobilizer state and both `vehicle_access` topics) are covered only by
hand-built payloads -- for those, "identical" is a statement about the decoder,
not about the vehicle.

Rerun either mode after s49 merges with `--ref <the commit before it>`; the
script reads the old module out of git and writes nothing.

## Gates this retired

`scripts/gates/s10.sh` asserted that no `google.protobuf` import remained and that
the package imported with protobuf absent. s49 reversed that decision on purpose;
`tests/client/test_proto_generated.py` and the two load-test runs are what guard
the dependency now. `s03`, `s08b`, `s09a`, `s09b` and `f5` key on
`rivian_client/parallax.py` by path and are historical for the same reason; what
they checked is held by `test_parallax_surface.py` and `test_parallax_golden.py`.
